# ADR: Абстракция Astro Provider

## Контекст

Это заменяемая интеграция с внешним сервисом для расчёта натальной карты. Основной результат, который нужен приложению, — положения планет в знаках, асцендент и набор триггеров для механизмов `astro_rules` и будущих `astro_triggers`.

Приложение не должно напрямую зависеть от формата ответа конкретного внешнего API. У разных провайдеров могут отличаться названия полей, способ авторизации, endpoint, формат координат, времени и часового пояса. При этом остальная часть бэкенда должна получать стабильную внутреннюю модель.

## Решение

Границей между приложением и внешними астрологическими API является интерфейс `astro.AstroProvider`:

```go
type AstroProvider interface {
    GetNatalChart(ctx context.Context, dob DateOfBirth, lat float64, lon float64) (NatalData, error)
}
```

Создание провайдера выполняется централизованно через `astro.NewProviderFromConfig` на основании переменной `ASTRO_PROVIDER`.

В текущей версии поддерживается нейтральный адаптер:

```text
ASTRO_PROVIDER=external
```

Это значение выбирает `internal/astro.ExternalAstroProvider`. Сейчас внутри этого адаптера используется FreeAstroAPI и endpoint:

```text
POST /api/v1/natal/calculate
```

Запрос отправляет дату и время рождения, координаты, `tz_str`, а также параметры `ayanamsha=lahiri`, `house_system=whole_sign` и `node_type=mean`.

Важно: название адаптера намеренно нейтральное. Если внешний API позже будет заменён, меняется реализация `ExternalAstroProvider` и маппинг ответа, а не создаётся цепочка неиспользуемых файлов под старые провайдеры.

## Обоснование выбора текущего внешнего API

В качестве текущего внешнего сервиса выбран `freeastroapi.com`, потому что его публичная документация описывает JSON API для расчёта натальной/ведической карты, включая положения планет, асцендент, дома и метаданные. Также сервис принимает координаты напрямую через поля `lat` и `lng`, а авторизация выполняется через заголовок `x-api-key`.

Использование координат предпочтительнее, чем передача названия города, потому что:

- входные данные становятся более явными;
- бэкенд не зависит от геокодинга внутри провайдера;
- проще заменить внешний API в будущем;
- проще тестировать маппинг и ошибки интеграции.

## Маппинг во внутренний формат

Любой внешний адаптер обязан приводить ответ API к внутренней модели `astro.NatalData`:

```go
type NatalData struct {
    Provider  string
    Planets   []PlanetPosition
    Ascendant *PlanetPosition
    Triggers  []string
}
```

Для текущей реализации `ExternalAstroProvider` используется следующий маппинг:

- `planets[].name` → нормализованное название планеты;
- `planets[].sign`, `sign_name` или `rashi` → нормализованный знак зодиака;
- `planets[].house` → номер дома;
- `planets[].degree` или `pos` → градус;
- `ascendant.sign` → знак асцендента.

После этого функция `BuildTriggers` формирует технические ключи и русские алиасы для совместимости со старым `ruleengine`.

Примеры технических триггеров:

```text
sun:cancer
sun_in_cancer
sun in cancer
moon:taurus
venus:taurus
ascendant:aries
```

Примеры русских человекочитаемых алиасов:

```text
Солнце в Раке
Луна в Тельце
Венера в Тельце
Асцендент в Овне
```

Технические ключи нужны для нового механизма `astro_triggers`. Русские алиасы нужны для совместимости с текущим механизмом `astro_rules`, где `ruleengine.Match` сравнивает входные значения с `astro_rules.name`. Если в базе уже есть правила с названиями вроде `Венера в Тельце`, они смогут продолжить матчиться без миграции всех правил.

## Конфигурация

Для реального вызова внешнего API нужны переменные окружения:

```text
ASTRO_PROVIDER=external
ASTRO_API_URL=https://api.freeastroapi.com
ASTRO_API_KEY=<secret>
```

Если `ASTRO_PROVIDER` не задан, используется значение по умолчанию `external`.

`FREE_ASTRO_API_KEY` временно поддерживается как fallback для совместимости с ранними локальными env-файлами. В новой конфигурации следует использовать `ASTRO_API_KEY`.

## Поведение при ошибках

Слой провайдера должен возвращать понятные ошибки как при технических сбоях, так и при некорректном ответе внешнего API.

Текущая реализация `ExternalAstroProvider` возвращает ошибки в следующих случаях:

- не задан API key: `ASTRO_API_KEY is not configured`;
- ошибка HTTP-запроса: `external astro natal chart request failed`;
- внешний API вернул неуспешный статус: `external astro natal chart unavailable: status=... body=...`;
- ответ невозможно замаппить: `external astro natal chart response does not contain planets or ascendant`.

## Заменяемость провайдера

В проекте намеренно используется один нейтральный HTTP-адаптер:

```text
internal/astro/external_provider.go
internal/astro/external_provider_test.go
```

Если внешний API будет заменён, например на другой сервис расчёта натальной карты, нужно изменить реализацию и тесты этого адаптера. При этом публичная граница остаётся прежней:

```text
AstroProvider -> NatalData -> astro_rules / astro_triggers
```

Обработчики, процессоры, построение prompt, `astro_rules` и `astro_triggers` не должны зависеть от структур ответа конкретного внешнего провайдера. Они должны работать только с `astro.NatalData`.

Старая модель `AstroProfile` удалена и не должна возвращаться как промежуточный формат.
